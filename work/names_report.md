# `work/names.json` — name-mining report

Generated by `scripts/names_json.py` (helpers: `scripts/names_records.py`).
Inputs are the decoded `ssi1` containers in `work/ssi/`, the extracted Boom
tree in `extracted/Boom/` (read-only), and the `.idd` UI bundles. Every
string below is **untrusted game data**.

**Result: 19,543 unique candidate names**, in two clearly separated tiers:

| tier | meaning | sources | count |
|------|---------|---------|-------|
| **hard** | verbatim plaintext, no inference | `vh`, `ndadata`, `idd_scripts` | 452 |
| **soft** | recovered from decoded `.bin` records via a structural walk | `fxstagemap`, `fxdynmapinfo`, `fxdynimginfo`, `fxstock`, `csysstr`, `csysqstr`, `fxstovi` | 19,912 (pre-dedup) |

`filterstr` (a profanity blacklist) is reported under `by_source` but **excluded
from `candidates`** — it is a moderation list, not an asset-name corpus. Listed
in `_meta.aux_sources`.

## 2. What was ruled out

Counted over every record recovered from the decoded `.bin` files:

| reason | count |
|--------|-------|
| CP949 Korean UI text (sentences, tooltips) | 6,349 |
| not an identifier (spaced text, `%s` format strings, HTML tags) | 326 |
| pure digits / numeric IDs | 174 |
| too short (< 3 chars) | 165 |
| generic English stopwords | 127 |
| contains whitespace | 94 |
| **total rejected** | **7,235** |

Also rejected/ignored:

- **`packagemap.ini.bin` has no names at all.** It is a pure numeric mapping
  table: `u16 count = 2508` then 2508 `(u32 left, u32 right)` ID pairs;
  `2 + 2508*8 = 20066` = exact file size. The `(u32,u32)` interpretation is
  *forced* by the exact size fit. It maps package IDs, not names.
- **`product.ini.bin`** — no string records; numeric (LE) table.
- **`fxstovs.ini.bin` / `channel2_001.ssd.bin`** — fixed-stride binary records,
  no names (`fxstovs` = repeated 12-byte `[u16..][u32..]` config rows).
- **`filterstr`** (186 entries: `byuntae`, `sibal`, `dds`-lookalikes, etc.) —
  kept in `by_source` for completeness, excluded from `candidates`.
- **`.dds` is NOT a used extension.** Zero plaintext `.dds` tokens and zero
  `DDS ` magics anywhere in the extracted tree. The extension list reflects
  evidence, not the brief's guess.
- Extension-like byte runs in `.idd` payloads that are **coincidental**, per the
  NOTES.md §2 correction: `.ExE`, `.iNi`, `.daT`, `.tgA`, `.sCr`, `.Tmb` each
  appear once, in the middle of what is clearly non-text binary.

## 3. Container structure recovered (generalises)

The NOTES.md §2 conclusion that these blobs are "opaque custom" is too strong.
The inflated `ssi1` payloads are **length-prefixed record tables**. Three
distinct schemes, all verified:

**(a) `[u32 len][payload]` — ASCII/Filename tables.**
`fxstagemap`, `fxdynmapinfo`, `fxdynimginfo`, `fxstock0..3`, `csysstr`,
`csysqstr`. Detected by validating `L` as a u32 followed by `L` printable
ASCII bytes at each offset, then keeping the non-overlapping set.
- `fxstagemap.ssd`: 436 records, 47.9% byte coverage, names `Monster01..48`,
  `Hidden01..`, `EBSMonster01..`, `DragonPalace01`, `Antarctic01`.
- `fxdynmapinfo.ssd`: `CaJJ_Space01`, `CaJJ_Camp08`, `Alche_Aqua`, `Aqua01..`,
  plus Chinese/Korean display names between the ASCII runs — hence the 33%
  coverage (the co-text is CP949, not counted as ASCII records).

**(b) `[u16 index][u32 len][CP949 text]` — string tables, 100% coverage.**
`stringtable.ini.bin`: `u16` little-endian index (descending, 6102, 6101, …)
+ `u32` byte length + CP949 text. **4,267 records, 353,198 / 353,200 bytes =
100.0% coverage.** This is the cleanest structure found and almost certainly
the template for the other `ssd` string files.

**(c) `[u16 count][u8 flag][u32 len][CP949 text]…` — small message tables.**
`csysfxmg.ssd.bin`: `u16 count = 31`, one flag byte, then 31 length-prefixed
CP949 records. `stringtable` differs only by the extra `u16` index per record.

**`csysstr.ssd.bin` is a key/value table.** Section 1 (offset 0x02) parses as
strict **ASCII-key / CP949-value alternation**: 1,598 ASCII keys
(`10FreeNiddle`, `150CharLimit`, `24CharLimit`, `2FreeNiddle`, …) each followed
by a CP949 value (`무료바늘 10개`, `[150자 이내]`, …). Coverage 42.9% because
the file continues with further sections after the key/value block.

These schemes fit the engine's `[u32 len][string]` idiom seen in the `.idx`
name fields — see §4.

## 4. Known-plaintext material for the `.idx` cipher agent

The `.idx` header is `ca da ef XX` / `u32 version=15` (NOTES.md §2). Everything
from 0x10 on is obfuscated. This work produced an unusual amount of plaintext
to attack it with:

1. **The plaintext asset paths from the `.idd` scripts are the *actual* names
   that the sibling `.idx` records encrypt.** For `ndadata/*` the `.idx` is a
   thin index (916 bytes for `21thBirthPopUp` vs 1.38 MB `idd`; `TwoDayFlow01`
   730 B vs 1.38 MB) listing the very paths found in the `.idd`. This gives
   position-tied plaintext guesses per archive.

2. **A strong structural fit was found on the FIRST record of every `.idx`.**
   The first name field always begins at **0x10**, ends in an ASCII fragment,
   and is immediately followed by a **plaintext `u32 size, u32 size, u32 0`
   trailer** (verified across four archives):

   | file | name field | tail bytes | trailer @ | size |
   |------|-----------|-----------|-----------|------|
   | `ndadata/21thBirthPopUp.idx` | 0x10..0x28 (24 B) | `E \x02\x08` **`.bmp`** | 0x28 | 2029 / 2029 / 0 |
   | `FxStage.idx` | 0x10..0x2B (27 B) | `\x04\x00` **`Star`** | 0x2B | 92066 / 92066 / 0 |
   | `fx.idx` | 0x10..0x22 (18 B) | `\rD` **`Back`** | 0x22 | 264284 / 264284 / 0 |
   | `FxSound.idx` | 0x10..0x1E (14 B) | `/\x1f` **`iens`** | 0x1E | 480189 / 480189 / 0 |

   So: **the name field is obfuscated, but its extension tail survives
   (`.bmp` is literally readable) and the size trailer is plaintext.**
   **Caveat:** the record chain does *not* continue — record 1 does not start
   immediately after the 12-byte trailer, and no plaintext length prefix is
   visible for record 1+. This matches NOTES.md's own note that "the length
   prefix scheme is NOT yet known", so treat this as a confirmed shape for
   record 0 and a strong hint, not a solved layout.

3. **The obfuscation is deterministic and position-stable within a field.**
   Aligning known `.idd` paths against `TwoDayFlow01.idx` / `SelectCandy.idx` /
   `FindNote.idx` produced **no zero-XOR run at any offset**, so it is not a
   fixed global keystream. But in `21thBirthPopUp.idx` a run of ~10 records
   starts with a **byte-identical ciphertext prefix** (`zues%Z.1:m\x14p~pm\x03\x00\x02\x04n\x02\x01B7pX\x06\x1c*%\x1d\x16\n50 6I…`)
   and differs only in the last few bytes. Equal plaintext at equal field
   offsets giving equal ciphertext is consistent with a **position-dependent
   transform (or a per-record key derived from the record)**, and it is
   deterministic. The usable consequence: **the same plaintext always yields
   the same ciphertext**, so one recovered crib decodes every copy of it —
   no need to attack each record separately.

4. **`.idx` byte 8 vs byte 12** are two counts (e.g. `FxStage`: 1150 / 1126;
   `21thBirthPopUp`: 0 / 27).

### Content matching: negative result

A whole-file search for each of the 34 `vh/*.bmp` inside every `.idd`/`.idx`/
`.pak` found **0 verbatim matches**. So the known-named `vh` sprites are *not*
stored uncompressed anywhere in the archives, and content matching cannot be
used to assign names to the 693 unnamed `FxSound` payloads or the others. (An
earlier probe that searched only a 48-byte slice produced 9 apparent hits; all
were false positives inside runs of identical `0xFF` bytes, e.g. white image
regions. The whole-file test is the sound one, and it is negative.)

## 5. Honesty about extraction vs. guesswork

- **Pure extraction (no inference):** `vh` (34), `ndadata` (92), and the
  `idd_scripts` paths (327). These are bytes read verbatim; the `idd_scripts`
  entries carry directory structure, so they are directly usable in a manifest.
- **Structural extraction with a validated decoder:** the `soft` names. The
  record *boundaries* are proven (length-prefix + encoding validation,
  100% coverage on `stringtable`), so the strings are real. What is *not*
  proven is that each one is an **asset filename** — many are quest/UI/config
  keys. Do not assume every `soft` entry resolves to a file.
- **Guesswork, explicitly flagged:** the `tga`/`ani`/`scr`/`eff`/`tmb`
  extensions rest on 1–7 token hits each and may be coincidental. The exact
  `.idx` cipher is not solved here — §4 is a structural finding plus a
  strategy, not a broken cipher.
- **Not attempted / still open:** `product.ini` and `channel2_001.ssd` are
  numeric tables; no names were recovered from them. The bulk of the large
  `.idd` archives (`FxMap`, `CharTE`, `EmoTE`, `fx`, …) is *not* plaintext
  markup — only 43 of ~80 archives yielded ASCII asset paths, so those remain
  where NOTES.md left them.

## 6. Applicability to the asset manifest

`work/assets/manifest.json` has 1,801 assets with `name: null`. How far these
names can actually fill it, honestly:

- **`ui_sprites` (34) is already fully named** (`vh/123.bmp` etc.) — nothing to do.
- **`ndadata_pak` (68)** — the bundle stems in `by_source.ndadata` give the
  *package* name, not the individual entries inside each `.idx`.
- **The 693 `FxSound` Oggs and the other carved payloads cannot be named from
  this data.** Their names live in the obfuscated `.idx` files, and per §4 the
  cipher is not broken. The whole-file content match (§4) is negative, so
  content-matching the `vh` sprites cannot name them either.
- **What this does supply** is (a) the `idd_scripts` path corpus, which is the
  *actual plaintext* the ndadata `.idx` name fields encrypt — i.e. ready-made
  cribs, and (b) the extension evidence (`.bmp` dominant, `.dds` absent).

So: the manifest's `name: null` gap is **not** closed by this work. What is
closed is the known-plaintext shortage for the cipher agent, plus a concrete
format finding (`.idd` carries plaintext UI markup).
